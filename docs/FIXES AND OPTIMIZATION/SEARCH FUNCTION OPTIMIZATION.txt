What is happening now

Imagine a user types:

Heinz

Your system currently behaves roughly like this:

User types "Heinz"
 ↓
 Search Users → possibly thousands of records
 ↓
 Search Properties → possibly thousands
 ↓
 Search Owners → possibly thousands
 ↓
 Search Receipts → possibly thousands
 ↓
 Search relationships → possibly thousands
 ↓
 Combine everything
 ↓
 Show maybe 10 suggestions

So you're potentially retrieving a huge amount of data just to display a handful of suggestions.

And if this happens after every keystroke:

H → search
 He → search
 Hei → search
 Heinz → search

That's unnecessary database and network traffic.

What you should change
1. Wait until the user stops typing

Don't search immediately after every key.

Wait about 300 milliseconds after their last keystroke.

Also, don't search for:

H

Wait until they enter at least 2 or 3 characters.

So:

H ❌
 He ✅ search after 300ms
 Hei ✅ new search
 Heinz ✅ new search

This is called debouncing.

5. Make the database good at searching

Your database currently uses searches like:

SQL
1
ILIKE '%Heinz%'
Show more lines

That basically means:

"Find anything containing the word Heinz."

That is fine functionally, but as your database gets bigger, it can become slower.

That's where pg_trgm indexes come in.

Think of an index like the index at the back of a textbook.

Instead of reading 500 pages trying to find "Heinz", you look in the index and immediately determine where it appears.

So you'd add indexes to fields people frequently search, such as:

Owner name
Property name
Address
Business name

You don't need to index everything.

What I would do first

Don't rebuild everything immediately. Do it in stages.

Stage 1: Quick fixes

Do these first:

✅ Add 300ms debounce
✅ Require at least 2–3 characters
✅ Change limit=5000 → limit=15
✅ Stop retrieving unnecessary columns

These should be relatively easy changes and can already make a significant difference.

Stage 2: Bigger improvement

In one sentence

Your system is currently searching too many places, retrieving too many records and making too many requests just to show a few suggestions.

The goal is to change it to:

Wait until the user pauses typing → send one request → search indexed data → return only the best 10–15 results.

My recommendation

Since your system is already working, don't jump straight to creating the entity_search table. Start with debounce + limit=15 + fewer columns, then consolidate the five searches into one RPC. Those changes alone may solve the performance issue without adding unnecessary complexity.
